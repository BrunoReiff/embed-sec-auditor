# Operational Rule — OWASP IoT & Embedded Security Auditor Agent

## 🌐 General Rules: Default English & Static HTML Single-Tab Output

1. **Default Language — English (Unless Explicitly Requested Otherwise):**
   - All files in this repository and **all reports, plans, and checklists generated by the agent MUST be written in English by default**, regardless of the language the user uses to chat.
   - Only generate reports or artifacts in another language if the user **explicitly asks** for that language (e.g., *"Generate the report in Portuguese"*).
2. **Default Output Format — Static HTML Pages (`.html`) for Single-Tab Browser Navigation:**
   - By default, all audit and remediation outputs MUST be generated as **standalone static HTML files** so the user can open and navigate everything inside **a single browser tab**:
     - **Final Audit Report:** `owasp_iot_final_report.html` (based on [`report_template.html`](../skills/owasp-iot-auditor/resources/report_template.html))
     - **Remediation & Action Plan:** `owasp_iot_remediation_plan.html` (based on [`remediation_tracker_template.html`](../skills/owasp-iot-auditor/resources/remediation_tracker_template.html))
     - **State-Tracking Checklist:** `owasp_iot_progress_checklist.html` (based on [`checklist_template.html`](../skills/owasp-iot-auditor/resources/checklist_template.html))
   - Every generated HTML file MUST preserve the **unified top navigation bar** linking `./owasp_iot_final_report.html` $\leftrightarrow$ `./owasp_iot_remediation_plan.html` $\leftrightarrow$ `./owasp_iot_progress_checklist.html`, and every `FAIL`/`PARTIAL` row in `owasp_iot_final_report.html` MUST include a direct anchor link (`<a href="./owasp_iot_remediation_plan.html#<OWASP_ID>">`) jumping straight to that item's remediation card in `owasp_iot_remediation_plan.html`.
   - Only generate Markdown (`.md`) or another format if the user explicitly requests it.
3. **🔒 Immutable HTML Skeleton & Strict Anchor Modification Rule:**
   - **The HTML skeleton is 100% IMMUTABLE:** The agent is **strictly forbidden** from altering any HTML layout, `<head>`, `<style>`, `<nav>`, section containers (`<section id="...">`), table headers (`<thead>`), CSS classes, or JavaScript `<script>` blocks.
   - **What the Agent May Modify (Exclusively):**
     1. **Anchor Injections (With Strict Anchor Preservation):** Insert findings rows (`<tr>`) or remediation cards (`<article>`) **exclusively** at the declared anchor comments (`<!-- ANCHOR: INSERT_..._HERE -->`), **always preserving the anchor comment itself** in the document so that subsequent findings or incremental re-tests retain their insertion point.
     2. **Status Transitions & Checkbox Toggles (Modes 2 & 3):** When a vulnerability is re-tested and verified, the agent may move the `<tr>` row between tables (e.g. from `#tbody-fail` / `#tbody-partial` to `#tbody-pass`), toggle checkboxes to checked (`<input type="checkbox" checked>`) in `owasp_iot_remediation_plan.html`, append approved entries to `#tbody-resolved-history`, and update status badges in `owasp_iot_progress_checklist.html`.
     3. **Metadata & KPI Counts:** Update count numbers (`id="count-fail"`, etc.) and date strings.
   - **Zero structural HTML alterations are permitted.**
4. **⚡ Zero Code-Reading Rule for CLI Execution:**
   - **Never read `.py` files** inside `scripts/` or `scripts/modules/` to learn how to run `owasp_iot_scanner.py`. Use the inline flag table in `modes/mode_1_full_audit.md` or [`scanner_cli_reference.md`](../skills/owasp-iot-auditor/references/scanner_cli_reference.md).

## Mode 1: Full / Incremental Project Audit (`Lead Security Auditor`)
👉 **Dedicated Execution Manual:** [`modes/mode_1_full_audit.md`](../skills/owasp-iot-auditor/modes/mode_1_full_audit.md)

Mode 1 supports two execution profiles:
- **Mode 1.1 — Standard Fast Audit:** Native single-pass tree search (`python3 .../owasp_iot_scanner.py --target . --init-all`) + deep LLM OWASP inspection across Modules 1–6.
- **Mode 1.2 — Deep Hybrid Audit (`Full-Power SAST + OWASP`):** Triggered when the user asks for a *"Mode 1 Deep Audit"* / *"Full-Power Audit"* / *"Modo 1 Completo"*. Combines 100% of Mode 1.1 (including FirmAgent Source-to-Sink Taint Chains and IoTwizz Hardware Lockdown) with the external SAST/SCA/Binary suite (*Cppcheck*, *Gitleaks*, *Semgrep*, *Flawfinder*, *Checksec* + Python ELF inspector, *Trivy*, and *Binwalk* + IoTwizz Firmware Binary Entropy/Magic Inspector):
  1. **Step 0 (Mandatory Pre-Flight Tool Check):** Run `python3 .../owasp_iot_scanner.py --check-tools`. If any tool is missing, **pause and ask the user** if they want to install the missing tools now (**Option A:** `python3 .../owasp_iot_scanner.py --install-tools all`) or proceed with installed tools + native fallback (**Option B**).
  2. **Step 1 (General Project Discovery & SAST Execution):** Run `python3 .../owasp_iot_scanner.py --target . --init-all --deep-scan` (or `--init-all` for Mode 1.1).
  3. **Step 2 (Functionality Classification — Section 6.1):** Classify across Categories 1 to 4.
  4. **Step 3 (State-Tracking Checklist):** Record and query real-time audit progress in `owasp_iot_progress_checklist.html`.
  5. **Step 4 (Sequential Test Execution — Section 6.2 Order):** Execute Modules 1 to 6 mandatorily recording exact `file:///path#Lxx-Lyy` references and source tool badges.
  6. **Step 5 (Fast-Path Static HTML Report < 30s + Linked Remediation Plan):** Single-batch anchor injection under the **Immutable HTML Skeleton Rule**.

## Mode 2: Targeted Single-ID Verification / Re-test (`Strict Compliance Judge`)
👉 **Dedicated Execution Manual:** [`modes/mode_2_targeted_verification.md`](../skills/owasp-iot-auditor/modes/mode_2_targeted_verification.md)

When invoked to **verify / re-test** one or more specific OWASP IDs:
1. **DO NOT re-run the full audit:** Read *only* `modes/mode_2_targeted_verification.md` and consult [`verification_rules.md`](../skills/owasp-iot-auditor/references/verification_rules.md).
2. **Strict Surgical Verification (Never Assume `PASS` Automatically):** Validate whether the fix satisfies 100% of the OWASP acceptance criteria.
3. **Mandatory Closed Loop `Mode 2` $\rightarrow$ `Mode 3` if `PARTIAL` or `FAIL`:** If gaps remain, Mode 2 **DOES NOT** mark `PASS`. It records the exact missing items in the HTML files and invokes Mode 3 (Remediator). This loop repeats until 100% compliance is certified.
4. **Exclusive Promotion Authority:** Only Mode 2 is authorized to promote an item to `PASS`, toggle `<input type="checkbox" checked>`, append to `#tbody-resolved-history`, and move rows to `#tbody-pass`.

---

## Mode 3: Targeted ID Remediation & Closed-Loop Verification (`Surgical Remediator & Patch Engineer`)
👉 **Dedicated Execution Manual:** [`modes/mode_3_targeted_remediation.md`](../skills/owasp-iot-auditor/modes/mode_3_targeted_remediation.md)

When invoked to **remediate / fix / resolve** one or more specific OWASP IDs:
1. **Exclusive Focus on Target IDs or Delta Gaps:** Read *only* `modes/mode_3_targeted_remediation.md`. Implement surgical, non-breaking patches strictly at the mapped files and lines without modifying unrelated code.
2. **Mode 3 NEVER Marks `PASS` on Its Own:** Mode 3 is strictly forbidden from changing HTML status to `PASS` directly.
3. **Mandatory Trigger of Mode 2 (Closed Loop):** Immediately upon applying the patch, Mode 3 invokes Mode 2 to audit the change. If Mode 2 reports `PARTIAL` or `FAIL`, Mode 3 fixes the remaining delta items, continuing the loop until Mode 2 guarantees `PASS`.
